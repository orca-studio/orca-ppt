# 转场连续性:改进说明

> 状态:第 1、2、3 条**已实现**;第 4 条测过、不改;第 5 条写成了规范里的表,曲线没动(2026-09-24)。
> 下文的现状描述和行号对应实现之前的 `c8a7297`。写于 2026-09-23。

本 skill 的价值就一句话,`references/transitions.md` 开篇写的:**观众要看得见连续运动**。
这份说明只收一类问题 —— 会让观众在**现场放映**时看不到连续运动、而**录制和自检发现不了**的地方。

为什么强调「录制发现不了」:`capture.mjs` 是离线逐帧 seek,不会有人在转场中途按键,也不会掉帧。
自检标准第 2 条(「转场第一帧和上一页最后一帧是否一样,不应该有跳变」)在录出来的视频里永远是过的。
所以下面几条,不改就只能靠演讲者在台上碰见。

## 关于参考来源

起因是对照了 Emil Kowalski 的动效 skill(emilkowalski/skills)。但他的原则是给**网页界面**定的 ——
按钮、菜单、弹层,用户一天操作几百次,追求「立刻有反应」。演示稿的转场是另一回事:演讲者按键,
观众只看一遍,语法来自剪辑和镜头。所以这里**不按他的规矩改**,只借了三条跨领域成立的技术事实:

1. 被打断的运动要从**画面上的当前值**接着走,不能先跳到终点再开始。
2. 逐帧改 `transform` / `opacity` 最便宜;逐帧改尺寸和位置会让浏览器每帧重排。
3. 两个不透明的东西同时对半淡,中间那一帧会透出背景(交叉溶解的「中点发虚」)。

他的另一些规矩**对本 skill 是错的**,不要搬:

| 他的规矩 | 为什么不适用 |
| --- | --- |
| 界面动画不超过 300ms | 那是控件反馈。转场是讲解,0.9–1.4 秒是对的,规范里的时长不要压 |
| 键盘触发的操作不做动画 | 那条针对一天按几百次的快捷键。翻页是演讲者按、观众看,每次只看一遍 |
| 一律不用 ease-in | 匹配放大、整页推近、遮挡剪辑是「加速进切点、减速出切点」的成对曲线,切点是最快的一刻 —— 这是剪辑手法 |
| 不从 `scale(0)` 起 | `grow-up` / `grow-right` 表达「从基线长出来」,从 0 开始才对 |
| 用弹簧、承接手势速度 | 翻页没有手势速度;逐帧录制要求时间确定,定时补间更合适 |

## 1. 中途翻页会跳帧(最要紧)

**现状。** 转场还没放完就按 →,Reveal 先切到下一页、发 `slidechanged`,
`runTransition` 第一件事是 `cleanup()`,它把正在跑的转场直接拨到终点再销毁
(`runtime/engine.js:1388-1395`,关键是 `1390` 的 `current?.progress(1).kill()`)。
然后下一次转场从上一页的**终态**快照开始。

观众看到的:A→B 飞到一半 → 画面瞬间变成 B 的终态 → B→C 开始。中间那一下就是跳帧,
正好打断本 skill 要的连续感。台上演讲者手快、或者翻过头又往回翻再往前,都会碰到。

**为什么不能简单修。** `slidechanged` 触发时 Reveal 已经把 C 显示出来了,而且这个事件取消不了。
A→B 的 ghost 挂在 B 里,B 一隐藏它就跟着看不见了。所以没法在事件里「接着放完」,只能在**翻页之前**拦。

**建议。**

- 引擎自己接管「往前翻」:用 Reveal 的 `keyboard` 配置把 → / 空格 / PageDown 指到引擎的函数
  (比如 `window.__orcaAdvance()`),不让 Reveal 直接翻。
- 这个函数:
  - 没有转场在跑 → 照常 `Reveal.next()`。
  - 有转场在跑 → `current.timeScale(...)` 把剩下的部分压到约 150ms 放完,`onComplete` 里再 `Reveal.next()`。
    代价是这次翻页晚约 150ms 开始,换来画面不跳。
  - 150ms 内又按了一次(连按)→ 当成「要跳过去」:直接硬切到目标页,不放中间的转场。
    这和现有规则「往回翻、跳页没有转场」一致。
- 往回翻不受影响,仍然硬切。

另一条路是「从半路的画面拍快照接着走」(不等,完全连续),但各个 builder 都假设上一页处在终态
(`box()`、`rectOf()` 量的都是终态布局),改动面大,不建议先做。

**会连带 orca-ppt 应用。** 应用里有三处绕过键盘直接调 `Reveal.next()`:
`apps/web/src/Stage.tsx:287`、`Stage.tsx:349`、`apps/web/src/guest/autoplay.guest.js:38`
(行号对应 orca-ppt 的 `6109dca`)。
引擎有了 `__orcaAdvance` 之后,那边要跟着改成调它,否则应用里的翻页和自动播放还是会跳。

**怎么验收。** 录制验不了(见开头)。建议给 `window.__capture` 加一个「在转场第 N 毫秒按下一页」的选项,
让 `capture.mjs` 能录一段「中途打断」,再按自检第 2 条检查打断那一帧前后是否连续。

## 2. 原地替换中途发虚

**现状。** `swapTween`(`engine.js:634-637`)让旧元素 1→0、新元素 0→1,同时、同曲线、同时长。
旧的压在新的正下方(`engine.js:822-826`)。

两个不透明的卡片同时对半淡:中点时新卡 50%、旧卡 50%,叠起来只盖住 75%,**背景透出来 25%**。
深色卡换深色卡时,中间会亮一下;浅底上换色块,中间会灰一下。观众读到的是「闪了一下」,
不是「换了一张」。(`transitions.md` 原地替换第 6 条讲的是两块底色互换会混色,是另一个问题。)

**建议。** 新的淡入,旧的**不跟着同时淡**:

- 新元素 0→1,时长 d;
- 旧元素保持 1,直到新元素基本不透明(约 0.6d)之后再在剩下的时间里淡掉,或者 d 时直接藏起。

新旧同位置、同尺寸(这正是原地替换的硬规则),旧的在下面被新的盖住,全程不会透出背景。
文字这类本身有透明区域的元素,旧字要在后半段淡掉,否则会从新字的空隙里露出来 —— 所以用「后半段淡出」,
不要用「最后一帧直接藏」。

**怎么验收。** 取转场中点那一帧,和前后两页比:背景色不应该出现在卡片范围内。

## 3. 「减少动效」要做成开关,不要自动跟系统走

**现状。** 整个 skill 没有任何减少动效的处理(`runtime/`、`references/`、`templates/` 里搜不到
`prefers-reduced-motion`)。整页推近是 2–8 倍的全屏缩放(`transitions.md` 整页推近第 2 条),
对晕动敏感的人最难受。

**但不要照网页的做法读 `prefers-reduced-motion`。** 放映时,是**演讲者电脑**上的系统设置在决定
**观众**看到什么,观众并没有选过。自动退化,等于演讲者在不知情的情况下把稿子的价值关掉了。

**建议。** 默认完整转场;给一个显式开关(URL 参数如 `?calm`,或 `<body data-motion="calm">`),
开了之后:

| 手法 | 退成 |
| --- | --- |
| 共享元素、形态变换、一变多、多合一、元素交接 | 保留,时长不变 —— 它们是讲清关系的那部分,去掉就只剩硬切 |
| 整页推近、放大进元素内部 | 换成约 0.4 秒原地淡化 |
| 运动模糊(`isoBlur` 等) | 关掉 |
| 匹配剪辑 | 不变(本来就是硬切) |

`?capture` 录制模式忽略这个开关。开关写进 `SKILL.md`,让 agent 知道有这回事、在用户提到
「有人会晕」「给长辈看」时主动加上。

## 4. 一变多、多合一、放大进元素:逐帧改尺寸(先测再决定)

**现状。**

- 一变多 / 多合一插值的是 `left / top / width / height` 和圆角(`box()` 在 `engine.js:847`,
  补间在 `901`、`941`)。
- 放大进元素内部每帧写替身的 `width / height / borderRadius`(`engine.js:495`)。

这些属性每帧都会触发重排和重绘。录制是离线逐帧,永远不会掉帧;现场放映在投屏的轻薄本上可能会。

**为什么先测不先改。** 这几个手法本身就是「形状变成另一个形状」:宽高比变了、圆角变了,
里面可能还有文字。换成 `scale` 会把圆角和文字一起拉变形,换成 FLIP 也要处理子元素的反向缩放 ——
不一定划算。元素都是绝对定位,重排的范围也有限。

**建议。** 先在一台弱机器上用 Chrome Performance 录一次一变多(8 个以上目标)和放大进元素,
看有没有掉帧。掉帧才改:位置部分(`left / top`)换成 `x / y` 是无风险的,先做这一半;
尺寸部分看测量结果再定。

## 5. 缓动写进规范(顺手)

**现状。** 缓动散在代码里,而且没有写理由的地方比写了的多:

- 共享元素走 Reveal 的 `autoAnimateEasing: "cubic-bezier(0.65, 0, 0.35, 1)"`(`engine.js:1452`)。
- 一变多、多合一用 `power3.inOut`(`901`、`941`)。
- 整页推近、放大进元素用 `power2.inOut`,注释说「power3 起步太慢,前 0.4 秒像卡住」(`engine.js:457`)。
- 退场用 `power1.in`(`828`、`898`、`939` 等)。

同一个「屏上移动」在不同手法里用了三条曲线;而 orca-motion-skill 的
`references/principles.md` 第 5 节又规定「镜头用 `power3.inOut`」,和上面那条注释的结论相反。

**建议。** 在 `transitions.md` 里加一张表:屏上移动 / 新元素入场 / 旧元素退场 / 镜头推拉,
各用哪条曲线、为什么。代码改成引用同一组常量。两个 skill 的「镜头」取同一个结论。

退场用 `power1.in` **不算错**:旧元素要「加速离开」,这是退场该有的样子。
只是要确认它在 0.6 秒新元素入场之前已经让出位置(`transitions.md` 第 5 条的延迟表就是在管这件事)。

## 实现记录(2026-09-24)

- **第 1 条**:往前翻的键交给 `advance`,宿主调 `window.__orcaAdvance()`。转场在跑时把剩下的部分压到 0.15 秒,
  等它真正放完(GSAP 的 onComplete、CSS 动画的 finished)再翻;这期间又按了就直接跳到目标页。
  实测 forest-bento 一变多放到 14% 时按 →:改前一帧跳过 1.8 秒动画;改后剩下的在几帧里快进放完。
  验证先在浏览器里逐帧记 GSAP 时间线进度;之后 `capture.mjs` 加了 `--interrupt 页号@毫秒`,
  能把「中途打断」录出来:forest-bento `--interrupt 2@480`,快进结束那一帧和下一页转场第一帧
  的差异是 0.0001(RMSE),换页处不跳。快进第一帧差异 0.45 —— 那是把 1.6 秒压进 0.15 秒,不是拨到终点;
  嫌快的话调长 `FINISH_S`。
- **第 2 条**:两边都有不透明底时,旧的垫在下面保持不透明,只让新的淡入;文字照旧同时淡。
  实测 `_tests/swap-text` 第 2→3 页牌面中点:改前 (76,48,35),改后 (132,78,45) = 两色平均。
- **第 3 条**:`?calm` / `data-motion="calm"`。整页推近、放大进元素、推近匹配换成 0.4 秒淡化,
  运动模糊关掉,其余照旧。实测 emerald-editorial 的整页推近:开关打开后 0.2 秒时是淡化,最后完整停在目标页。
  规范写进 `transitions.md`「减少动效」,SKILL.md 告诉 agent 什么时候该打开。
- **第 4 条**:无头 Chrome、CPU 限速 6 倍,一变多 / 放大进元素 / 多合一和只动 transform 的整页推近
  一样稳在 60 帧,没有一帧超过 50ms。按「掉帧才改」不动代码。没模拟慢 GPU,真机投屏还可能不同。
- **第 5 条**:各用途实际在用的曲线写成 `transitions.md` 的「缓动曲线」表,曲线值没改 ——
  一变多 / 多合一的 `power3.inOut` 要不要统一成 `power2.inOut`,得录出来并排看过再定;
  orca-motion-skill 的「镜头用 power3.inOut」和引擎的结论相反,那边还没改。
